## A · 工具与流程

### A1 🔴 `$finish` 会终止整个 do 脚本，后续 TB 静默跳过

- **症状**：一个 `.do` 里串跑 4 个 TB，`vsim -c -do "do run_all.do"` 退出码 0，日志看起来正常，但**只有第 1 个 TB 真的跑了**。
- **根因**：testbench 末尾的 `$finish` 结束的是整个 vsim 会话，不是「当前这一次 run」。do 脚本里 `$finish` 之后的所有命令都不会执行。
- **代价**：一整轮迭代里，我们以为 4 个 TB 全绿，实际只跑了 1 个。
- **正确做法**：**每个 TB 一个独立 vsim 进程**。见 [`sim_modelsim/run_all.bat`](../../furuta_lqr_ctrl/sim_modelsim/run_all.bat)——5 次独立 `call vsim`，编译单独放在 `compile.do`。

### A2 `quit -f` 同样会终止 do 脚本

- **症状**：`-do "run -all; quit -f; do next.do"` 里 `next.do` 从不执行。
- **根因**：与 A1 同源。`quit -f` 是强制退出会话。
- **正确做法**：`quit -f` 只能是该 vsim 进程的**最后一条命令**。

### A3 🔴🔴 `$finish` 使 vsim 退出码恒为 0，`errorlevel` 对判决完全失明

- **症状**：TB 打印了 `[FAIL]`，但 `if errorlevel 1 goto error` 不触发，脚本报「全部通过」，退出码 0。
- **根因**：`Errors: 0, Warnings: 0` 是 **ModelSim 自己的 elaboration/runtime 计数器**，它**不统计 `$display` 输出的判决字符串**。TB 用 `$display` 报 FAIL 然后 `$finish`，在 vsim 看来这是一次完全成功的运行。
- **代价**：**这是本项目五次假绿事故的共同机制**（见 §C1）。
- **正确做法**：脚本必须对每步做**双重校验**——
  1. 日志里**不能出现**失败标记：`[FAIL]` / `[ERROR]` / `** Error` / `** Fatal` / `HIL RESULT: FAIL` / `DIVERGED`
  2. 日志里**必须出现**该步的成功标记：`[ALL PASS]` / `ALL PASSED` / `100%` / `HIL RESULT:`

  第 2 条同样重要：如果 TB 因为 A1 根本没跑，第 1 条检查会通过（没有 FAIL），只有「成功标记缺失」能抓到它。
- **验证过有效**：新脚本第一次运行就抓到了一个 `vlog-2730 Undefined variable` 编译错误，并在此后如实以退出码 1 报告 TEST D 失败。

### A4 Tcl 中 `echo "[1/3]"` 的方括号被当作命令替换

- **症状**：do 脚本报错，提示找不到命令 `1/3`。
- **根因**：Tcl 里 `[...]` 是命令替换语法，`"..."` 不阻止它。
- **正确做法**：用花括号 `echo {[1/3]}`，或转义 `echo "\[1/3\]"`。

### A5 需要入库的脚本不能放在被 `.gitignore` 忽略的目录

- **症状**：报告里写「运行 `gw_sh.exe impl\build.tcl`」，但 `impl/` 整个被忽略——**克隆仓库后这条命令直接失效**。
- **根因**：Gowin 的产物目录 `impl/` 必须忽略（二进制、体积大、每次重建），但构建脚本是源码。
- **正确做法**：构建脚本放项目根（`build.tcl`），产物目录保持忽略。文档里给出的每条复现命令都要问一句「克隆后它还在吗」。

### A6 PowerShell 控制台中文乱码，导致误判「匹配失败」

- **症状**：`Select-String -Pattern "同步|失步"` 输出全是 `?????`，看起来像没匹配到。
- **根因**：控制台输出编码不是 UTF-8。
- **正确做法**：
  ```powershell
  $OutputEncoding = [System.Text.Encoding]::UTF8
  [Console]::OutputEncoding = [System.Text.Encoding]::UTF8
  git -c core.quotepath=false ls-files    # 让 git 输出可读中文路径而非 \345\245 转义
  ```

### A7 移动中文名文件用 `Move-Item` + `git add -A`，不用 `git mv`

- **原因**：`git mv` 需要把中文文件名作为参数传递，在某些 shell 编码配置下会被破坏。
- **做法**：`Move-Item` 原生处理 Unicode 无问题，随后 `git add -A` 让 git 自己识别重命名。**实测 6 个中文文件名全部识别为 `R` (rename) 且相似度 100%**，历史完整保留。

### A8 每次综合后必须确认顶层模块

- **症状**：综合跑通了，但综合的是 `furuta_lqr_ctrl`（一个子模块）而不是 `j280_hw_top`。所有时序数据都是错的对象的。
- **正确做法**：综合后 grep 日志里的 `Current top module is "j280_hw_top"`。**不要只看「有没有报错」。**

### A10 `vmap` 会静默改写被 git 跟踪的 `modelsim.ini`

- **症状**：手工跑了一次 `vmap work work_cjk` 做实验后，`git status` 出现 `M sim_modelsim/modelsim.ini`。
- **根因**：`modelsim.ini` 里的 `work = work` 是库映射，`vmap` 会**就地改写**它。而该文件是**被 git 跟踪的**：
  `.gitignore` 里虽然有 `sim_modelsim/*.ini`，但**已跟踪文件不受 gitignore 影响**。
- **正确做法**：

  做完再确认一次。

## B · 定点数学

### B1 🔴🔴🔴 改 Q 格式必须同步改移位量（本项目最贵的一个坑）

- **症状**：起摆时能量判据几乎立刻认为「能量已达标」，切断泵能，摆杆永远起不来。
- **根因**：为了降位宽把角速度从 Q16 改成 Q12 参与平方，但缩放移位 `>>> 8` **没有跟着改成 `>>> 24`**。结果 `e_kin` **虚高 65536 倍**。
- **量化影响**：只要 |θ̇| > **0.067 rad/s**（几乎任何微小摆动）就会误判 `E ≥ 0` → `energy_deficit = 0` → 停止泵能。
- **代价**：**耗费一整轮迭代**才定位。而且它藏在「已经修好 N1~N5」的提交里，当时所有 TB 都是绿的。
- **正确做法**：
  1. 改任何 Q 格式时，把该表达式链路上的**每一个**移位量重新推导一遍；
  2. 用 Python 逐位复现 RTL 的定点路径，对若干组输入比对中间量（不只是最终输出）；
  3. 断言中间量的**精确数值**，不要只断言最终 1 bit（见 §C2）。

### B2 🔴🔴 查表索引的步进必须与表本身的步进一致

- **症状**：θ 较小时 cos 值正确，θ > 114° 后**符号翻转**（θ=120°/150°/170° 全部错）。
- **根因**：`idx = abs_theta_q16[16:11]` 的步进是 1/32 rad = **1.79°**，而 64 点表覆盖 0~π 的隐含步进是 π/63 = **2.86°**。两者不匹配，θ ≥ 2.0 rad 时索引回绕。
- **后果**：起摆过程中大部分行程能量泵在**抽取**能量而不是注入。
- **正确做法**：`idx = (q16 × 20535) >>> 26`，其中 20535/1024 ≈ 63/π。**并且要对全区间做数值验算**（修复后全区间最大误差 4.7%，零符号翻转）。

### B3 🔴 耦合常数不能当作独立修正量分别改

- **症状**：按建议改了 tanh 折线的段 3 常数（37027 → 36428），x=0.5 处跳变从 0.0103 改善到 0.0011，但 **x=1.0 处从 0.0050 恶化到 0.0092**。
- **根因**：段 2 与段 3 的常数**共同**决定边界连续性。把它们当成两个独立修正量分别处理，必然顾此失彼。
- **代价**：一轮返工。
- **正确做法**：改分段折线时，**把所有段的边界值联立求解**，然后对每个边界点都验算。任何「只改一个常数」的建议都要先问：它和别的常数耦合吗？

### B4 🔴 钳位值必须由物理临界点决定，不能凭直觉

- **症状**：起摆 runaway——机械能一路涨到 +164 mJ，转臂角速度爆表，永远进不了捕获窗口。
- **根因**：动能钳位在 **8 rad/s**，使 `e_kin` 上限只有 **1407**，而势能幅值 `|e_pot|max = 6428`。于是 `e_kin + e_pot` **永远为负** → `energy_deficit` **恒为 1** → 泵能永不停止。
- **物理依据**：要让动能有可能抵消势能，需要 θ̇ ≥ `sqrt(4·m2·g·l2/Jp)` = **17.151 rad/s**。HIL 实测起摆期 |θ̇| 峰值达 **19.5~20.4 rad/s**，全部超过该临界点。
- **正确做法**：钳位阈值与钳位值**同时**放宽到 ±32 rad/s（阈值 `2097151`、值 `131071`）。
- **额外教训**：**上一轮给出的修法方向是错的**——只改阈值不改值，或只按「看起来合理」的数值取钳位，都没有回到物理临界点。定常数前先算物理量级。

### B5 补码非对称：正负钳位值的 e_kin 差 1 LSB

- **现象**：`+32.0 rad/s`（q16 = 2097152）满足 `> 2097151` 走钳位分支得 **131071**，`e_kin = 22527`；`−32.0 rad/s`（q16 = −2097152）**不满足**严格小于 `< −2097152`，走位选择分支得 **−131072**，`e_kin = 22528`。
- **影响**：写 TB 断言时正负用例**不能用同一个期望值**。
- **正面价值**：这 1 LSB 差异恰好是验证负向路径未被错误处理的**敏感探针**，值得显式断言。

### B6 差分测速必须做最短角位移解卷绕

- **症状**：θ 跨越 ±180° 时 `raw_dtheta` 出现 **−6283 rad/s** 的假尖峰，真实值只有 34.9 rad/s——**差 179 倍**。
- **根因**：`diff = θ_now − θ_prev` 在 +179° → −179° 时得到 −358°，而真实角位移只有 +2°。
- **正确做法**：加阈值判断与平移——
  ```verilog
  if      (diff >  205887) diff = diff - 411775;   // > +pi  -> 减 2pi
  else if (diff < -205888) diff = diff + 411775;   // < -pi  -> 加 2pi
  ```
- **连带坑**：加了这个逻辑后 **Fmax 从 57.685 崩到 50.194 MHz**（裕量仅 0.39%）——比较 mux 与 ×1000 串在 64 位乘法之后。必须拆流水（见 §E2）。

### B7 禁止使用除法器

- **症状**：6 处 32/64 位除法导致资源暴涨、时序恶化。
- **正确做法**：一律「乘法倒数 + 移位」。例：`/1000` → `* 0x6666 >>> 16`。
- **注意**：倒数常量的精度要验算。`/1000` 用 `0x6666/65536 = 0.99997` 有 0.003% 误差；本项目 1 ms 积分步长用 `(x>>>10)+(x>>>16)+(x>>>17)` 逼近 `×0.001`，误差 0.05%——**要清楚自己接受的是哪个精度**。

### B8 常量必须与配对常量自洽

- **症状**：`RAMP_STEP_Q16` 从 572 改成 57（降速 10 倍），但速度前馈 `RAMP_VEL_Q16` 仍是 571998。
- **后果**：前馈项 `K4 × dalpha_err` 产生 **−39.49 V = 3.29 × 12 V 轨**的荒谬命令。
- **不变式**：`RAMP_VEL_Q16 == RAMP_STEP_Q16 × 1000`（1000 = 每控制周期的 ms 数换算）。
- **正确做法**：这类成对常量要写成注释里的**显式不变式**，改一个时必须检查另一个。

### B9 🔴 有符号算术右移 `>>>` 向负无穷截断（floor）导致非对称积分漂移与死区

- **症状**：LQI 积分器在零点附近出现慢极限环，系统长期以 ±0.8° 振荡，长时间运行后积分器单向撞死在负限幅（-16384）。
- **根因**：原实现 `int_step = (alpha_err >>> 10) + (alpha_err >>> 16) + (alpha_err >>> 17)`。在 Verilog 中有符号数 `>>>` 采用向负无穷取整（floor）：
  - 当误差在 $[0, +0.895^\circ]$（Q16 为 $[0, 1023]$）时，三项皆为 0，增量为 **0**（积分完全不起作用的死区）；
  - 当误差在 $[-0.895^\circ, 0]$（Q16 为 $[-1023, -1]$）时，每一项都向下截断为 -1，三项相加恒为 **-3**！
  - 对称小幅摆动时，积分器每毫秒净累加 -1.5，产生负向单边自激漂移，与电机死区电压耦合形成持续极限环。
- **代价**：导致拓展要求 1 的实际静差在退出测量尾窗后反弹，未能达到赛题要求的「平滑移动到指定方向并保持静止」。
- **正确做法**：
  1. 废弃每拍预除以 1000 的有损做法，改用 **32 位全精度累加器 `alpha_int_accum`**，每毫秒直接累加 `alpha_err_q16`（即使 1 LSB / 0.00087° 误差亦能积累）；
  2. 输出换算扩展至 34 位采用无 DSP 移位加法：`accum * 131 = (accum <<< 7) + (accum <<< 1) + accum`；
  3. 引入 `+ 34'sd65536` 对称四舍五入偏置再 `>>> 17`，实现正负误差绝对对称的除以 1000 缩放。

### C2 🔴 只比对 1 bit 的断言等于没有断言

- **症状**：53 个测试向量全部只比对 `energy_deficit` 这 1 bit，全绿。
- **根因**：`|e_pot|` 最大只有 6428，所以**任何** `e_kin > 6428` 都会让 `deficit = 0`。钳位值在 **[76200, 131071]（41% 宽的区间）** 内写错都测不出来：

  | 钳位值 | e_kin | deficit | 能否检出 |
  | ---: | ---: | :---: | :--- |
  | 131071（正确） | 22527 | 0 | — |
  | 110000（错） | 15866 | 0 | ❌ deficit 看不出，✅ e_kin 可检出 |
  | 92682（错） | 11264 | 0 | ❌ 同上 |
  | 76201（错） | 7614 | 0 | ❌ 同上 |

- **正确做法**：断言**中间量的精确数值**。本项目加了 `check_case_full`，同时比对 `e_kin_q16` 与 `e_pot_q16`，并用 `badmask`（1=deficit 2=e_kin 4=e_pot）定位是哪一项失配。
- **可观测性技巧**：`e_kin_q16`/`e_pot_q16` 是 Stage 1 的**组合**输出，看似不可采样；但它们的输入 `dth_sq_s0`/`cos_q14_s0` 是 Stage 0 寄存器，**在 `calc_en` 之后保持到下一次 `calc_en`**，所以 `tick_calc()` 返回后可以稳定读取。纯观测，不产生反馈路径，不改 RTL。

### C3 🔴 测量窗口错位，数值失真 5.7 倍

- **症状**：TEST D 报稳态位置误差 **10.155°**，远超 0.20° 容差。
- **根因**：尾窗起点按**固定偏移**算（`tick_idx + (n_ticks − 150) − TAIL_AVG_MS`），其中 `150` 隐含假设斜坡 90 ms 走完。斜坡速率改到 0.05°/ms 后实际需 **904 ms**，于是尾窗只在斜坡结束后 395 ms 打开——**正好罩住过冲衰减段**。
- **验证方法**：逐点重算 TRACE 里该窗口的数据，均值 ≈10.1°，与报告的 10.1550° 吻合 → **证明不是计算 bug，是窗口选择 bug**。
- **代价**：这个失真数字曾让我们把注意力放在「控制器收敛慢」上，而真正的问题是测量本身。
- **正确做法**：**窗口锚定到实测事件，不锚定到固定偏移**。
  ```verilog
  ramp_guard = 0;
  while (u_dut.alpha_ref_q16 != 32'sd51472 && ramp_guard < 3000) begin
      wait_ctrl_ticks(1);  ramp_guard = ramp_guard + 1;
  end
  wait_ctrl_ticks(TAIL_SETTLE_MS);   // 沉降
  traj_tail_start = tick_idx;        // 锚定实测时刻
  wait_ctrl_ticks(TAIL_AVG_MS);
  ```
  同时把预算 `TRAJ_PLAN` 提到能容纳「斜坡 + 沉降 + 尾窗」，并把入口守卫从 `>= 300` 提到 `>= 2700`——**预算不足时要响亮地跳过，而不是安静地测一个截断窗口**。

### C4 🔴🔴 测量平台自己有 bug，被测对象的误差被误归因

- **症状**：定点伺服稳态误差偏大，plant 报 α = 53.119°，DUT 报 54.539°，差 **1.420°**。当时被解读为「控制器收敛慢」。
- **根因**（在被测对象之外）：plant 模型的 `refresh_outputs` 每 **2 µs** 跑一次，但它读的 `alpha` 只在 `phys_now`（每 **200 µs**）由 RK4 更新。一个 RK4 步内可用的脉冲增量是
  ```
  dpulse = |dalpha| × dt_phys × CPR/(2π) = |dalpha| × 0.12732
  ```
  当 **|dα| > 7.854 rad/s** 时 `dpulse > 1`，正交目标索引一次跳 2 以上 → `encoder_quad_reader` 看到非法跳变（如 `4'b00_11`）→ 命中 `default: count_step = 2'sd0` → **静默丢计数，无任何告警**。
- **代价**：实测丢了 **16 脉冲 = 1.42°** 的系统性偏置，跑了整整 8 秒、被打印 2 次、被 **0 条判据**检查。
- **正确做法**（两件事都要做）：
  1. **修 plant**：维护 `pulse_emitted`，每次刷新**最多前进/后退一个状态**，保证 encoder 永远看到合法序列 `00→10→11→01`。余量核算：2 µs 刷新 → 上限 5×10⁵ 脉冲/s = **785 rad/s**，而实测峰值仅 7.6 rad/s，余量约 100 倍。
  2. **给测量平台自己加断言**：每个控制周期比对 plant 真值与 DUT 解算值。这是唯一能自动捕获失步的手段。修复后偏差峰值归零。
- **`state_load` 陷阱**：`pulse_emitted` 必须在 TB 重新摆位时同步到当前 α，否则单步逼近会从旧位置一路追赶，**产生一串虚假脉冲污染 DUT 计数**。

### C5 🔴 两个 always 块对同一 `real` 状态的竞态，命中率 100%

- **症状**：仿真结果依赖仿真器调度顺序；开关 `-voptargs=+acc` 就可能改变结论。
- **根因**：状态推进块用**阻塞赋值**写 `alpha/theta/...`（`real` 类型），另一个块在同一 `posedge clk` 调用 `refresh_outputs` 读它们。Verilog **不定义**同一事件触发的两个 always 块的相对顺序。
- **为什么是 100% 而非偶发**：两个计数器同源于 `rst_n`——
  ```
  phys_now 为真  ⇔  clk 序号 k ≡ 0 (mod PHYS_CYCLES = 10000)
  out_cnt 到期   ⇔  k ≡ 0 (mod OUT_REFRESH_DIV = 100)
  ```
  `k ≡ 0 (mod 10000)` **蕴含** `k ≡ 0 (mod 100)`，所以**每一次 RK4 积分都恰好落在一次传感器刷新的同一个时钟沿上**。
- **为什么必须修**：TEST B 的判据余量只有 **0.303°（1.4%）**，完全在这种非确定性的可翻转范围内。**一个用来出验收结论的平台必须是可复现的。**
- **正确做法**：合并为**单一 always 块**，顺序固定为「先推进状态，再刷新传感器输出」。发散检测放在 `if/else` 外面保证每拍都执行。代价是复位从异步变同步（对 TB 无影响）。

### C6 🔴 PASS 文本为一条从未执行的检查背书

- **症状**：日志打印 `[PASS] 待机态正确 (HANGING), 摆杆静止下垂, 编码器与 PLANT 同步`。
- **真相**：该处唯一的判据是 `if (u_dut.fsm_state !== 2'd0)`。「编码器与 PLANT 同步」**只打印对比值、从不比对**。
- **代价**：这是 C4 那 16 脉冲偏置能活过整个 8 秒运行的直接原因。
- **正确做法**：**PASS 文本里的每一个断言都必须有对应的判据**。写 PASS 消息时逐句自问：这句话我真的检查了吗？

### C7 「0 次异常」可能是平凡结果，不构成证据

- **症状**：解卷绕探测器报「假尖峰 0 次」，看起来修复生效。
- **问题**：如果 θ **从未接近 ±180°**，0 次尖峰是必然的，说明不了任何事。
- **正确做法**：判据要**同时要求覆盖**。本项目 TEST A2 是三分支：
  ```
  尖峰 != 0        → FAIL（解卷绕失效）
  穿越次数 == 0    → FAIL（路径未覆盖，0 次尖峰不构成证据）
  否则             → PASS（跨越 N 次 + 尖峰 0 次）
  ```
  穿越计数用 150000 Q16（131°）阈值：只有从 >131° 跳到 <−131°（或反向）才算真跨越，避免把普通摆动误计。实测跨越 **6 次**、尖峰 **0 次**。

### C8 只测正向路径，负向零覆盖

- **症状**：53 个测试向量**全部** `dtheta >= 0`。
- **后果**：`swing_up_ctrl.v` 的 `< −2097152 → −131072` 分支**从未执行**，`dtheta_rad_s_q16[21:4]` 对负数的**符号保持从未验证**。而起摆是**双向**泵能，反向路径与正向同等关键。
- **正确做法**：加负向镜像用例（−8.0 / −17.151 / −32.0 / −40.0 rad/s）。配合 B5 的 1 LSB 差异，负向钳位边界是个天然的敏感探针。

### C9 注释声称的覆盖数与实际不符

- **症状**：TB 注释写「完整 5×7 矩阵扫描（35 组）」，实际源码里只有 **19** 组。
- **正确做法**：**数源码里的调用次数，不要信注释**。`Select-String -Pattern "^\s+check_case(_full)?\(" | Measure-Object`。

### C10 断言陈旧但测试仍绿

- **症状**：`furuta_lqr_ctrl_tb` 断言 LQI 核延迟为 **3 拍**，而 RTL 早已改成 **4 级流水**。测试一直绿。
- **根因**：断言过松或恰好仍被满足，改动没有触发它。
- **正确做法**：**改流水线深度时必须同步改延迟断言**。更好的做法是让延迟断言精确到拍数（`== 4`），这样任何深度变化都会立刻报错。

### C11 期望值必须用与被测端相同的常量算，不能用浮点近似

- **症状**：TB 驱动 `DTH_17_15 = 32'sd1124068`，而验证脚本用 `17.151 × 65536 = 1124008`——**两者差 60**，导致 `e_kin` 期望值算成 6470 而非 **6472**。
- **后果**：断言会**假 FAIL**，然后你去查一个根本不存在的 RTL bug。
- **正确做法**：验证脚本直接读 TB 里的 localparam 常量值代入，或逐位复现 RTL 的定点路径。**先确认期望值本身是对的，再去怀疑 RTL。**

### C12 「Errors: 0, Warnings: 0」不代表任何事

- 见 A3。补充一点：ModelSim 的这个计数器**只统计它自己诊断出的问题**（语法、elaboration、运行时 X 传播等）。你的 `$display("[FAIL] ...")` 在它眼里只是一行普通输出。

### C13 🔴 监视器使能时序错位导致断言恒真（死分支）与跳过漏检

- **症状**：HIL 判据 0b 无论硬件如何修改、甚至故意注入失步都显示 `[PASS]`；若中途跳过用例，仿真依旧报全绿通过。
- **根因**：
  1. 待机阶段判据 0b 检查发生在 `mon_en=1` 之前，此时监视器计数器从未激活，`sync_desync_n` 恒为 0，检查变成了 `0 == 0` 恒成立；且闭环运行全程再无汇总检查；
  2. 若因前置条件不满足跳过后续测试，TB 只打印跳过说明而不累加 `n_fail`，`n_checks` 也未被触发，使得 `n_fail == 0` 依然成立，汇总打印 `HIL RESULT: PASS (N/N)`；批处理脚本仅用 `findstr` 匹配字符，直接误判。
- **正确做法**：
  1. 待机阶段即打开监视器，并在总结段加入**全仿真周期覆盖强断言**：`sync_desync_n == 0 && sync_th_desync_n == 0`；
  2. 总结段加入执行完整性断言：`if (n_checks < 10 || test_b_run == 0 || ...) n_fail++`，强制做到“跳过即失败”；
  3. 批处理脚本严格匹配 `(10/10` 标记，双重锁定。

## D · 控制算法

### D1 🔴🔴 积分分离用「清零」而非「冻结」

- **症状**：定点伺服过冲 **12.2°（27%）**，2 秒仍不收敛；稳态位置误差 1.1°。
- **根因**：`|alpha_err| > 10°` 时执行 `alpha_int_q16 <= 32'sd0`。斜坡期间积分器合法地累积了约 **−9000 Q16** 的跟踪补偿（这正是跟随移动参考所需的前馈），**过冲突破 +10° 的一瞬间全部被抹掉**，之后只能以 `int_step ≈ 10 Q16/ms` 从零重建（1 秒才 0.15 rad）。
- **量化证据**：实测 `alpha_int_q16 = 208`，而限幅是 ±16384 —— **积分器只用了 1.3% 的量程**，积分作用几乎被完全废掉。
- **正确做法**：窗口外**冻结**（`alpha_int_q16 <= alpha_int_q16`），停止累加但保留值。真正的清零只留给**离散事件**：
  ```
  !fsm_motor_active     停机
  !lqr_en               离开平衡态（起摆 / 保护）
  reset_integral_pulse  捕获切入瞬间
  soft_limit_err        软限位保护
  ```
- **实测效果**：`alpha_int_q16` 208 → **−2002**（1.3% → 12.2% 量程），稳态误差 **1.1017° → 0.2302°**（4.8 倍改善）。
- **⚠️ 这里有一个反直觉的陷阱**：**Python 黄金模型 `controller.py#L326` 也是清零**。为什么模型没暴露这个缺陷？因为 `test_suite.py::test_position_tracking` 用的是 setpoint **阶跃**（`dalpha_ref = 0`、无斜坡），误差从第一拍就 >10°，**积分器从未累积过任何东西**，所以清零与冻结在该用例下**完全等价**。
  > **元教训**：黄金模型没报错不等于 RTL 错了，**也不等于 RTL 对了**。要先问：模型的测试用例能不能触发这条分支？本项目的结论是：赛题拓展要求 1 明确要求「**平滑地**移动」，斜坡是必需的，而斜坡场景下清零会抹掉跟踪补偿——所以 RTL **有意偏离模型**，并在代码注释与报告 R15 里记录理由，**防止后续被「修正」回去**。

### D2 🔴🔴 硬编码判据冒充实现

- **症状**：综合通过、TB 全绿、资源正常——但起摆完全不工作。
- **根因**：`assign energy_deficit = 1'b1;`。整个能量判据「实现」就是一个常量。Python 模型里的 `if E < 0: pump else: a_pump = 0` 在 RTL 中**完全缺失**。
- **为何难发现**：它看起来像一行合理的默认值，而且当时 TB 没有任何用例需要 `deficit = 0`。
- **正确做法**：审查时搜 `assign .* = 1'b[01];` 与常量返回，**逐个问「这里本来应该是什么逻辑」**。

### D3 捕获窗口只有角度判据

- **症状**：θ 刚进入 ±22° 就切 BALANCE，但此时 θ̇ 可能很大 → **立刻甩出去**，反复振荡。
- **正确做法**：**双重捕获条件** `|θ| < 22° 且 |θ̇| < 4 rad/s`。

### D4 PROTECT 态不写 `current_state` 导致永久锁死

- **症状**：一旦进入保护态就再也出不来。
- **根因**：PROTECT 分支只做了输出保护，**没有更新状态寄存器的退出路径**。
- **正确做法**：保护态必须有明确的清除条件与回跳路径（本项目已实现并验证自恢复）。

### D5 捕获瞬间有 3~4 ms 控制空窗

- **症状**：切入 BALANCE 的那一刻摆杆已经甩出窗口。
- **根因**：LQR 只在 BALANCE 态计算，SWINGUP 期间不算——切换后才开始算，而流水线有延迟。
- **正确做法**：**LQR 后台常开**，FSM 只决定「用不用它的输出」，而不是「算不算」。

### D6 斜坡末端前馈单拍归零造成命令阶跃（已闭环达成，R1 消除）

- **现象**：`ramp_vel_q16` 从 57000 **单拍归零** → `dalpha_err` 突增 0.8698 rad/s → 经 `K4 = −4.5250` 产生 **−3.94 V（33% 轨）的单拍命令阶跃**。
- **影响**：方向是对的（制动），但属硬冲击；紧随其后 |θ| 冲到 3.85° 峰值。
- **修复与闭环**：
  1. `traj_gen.v` 引入 `vel_decay_cnt` 状态机，在斜坡末端分 2 拍平滑右移衰减速度前馈（57000 → 28500 → 14250 → 0）；
  2. 配合 B9 全精度累加器消除积分死区与单边漂移，定点伺服绝对稳态误差由 0.2302° 进一步收敛至 **0.1923° < 0.20°**，R1 彻底闭环关闭。

### D7 PWM 死区补偿与极限环振荡防范

- **澄清与真相**：早前曾记录死区补偿需设为 250（对应 3.0V）。但在具有高精度积分器的闭环系统中，**硬加死区跳变（正负 250 瞬变）会直接在平衡零点附近激发高频极限环抖颤（Limit Cycle）**。
- **正确做法**：顶层 `j280_hw_top.v` 显式设置 `.DEAD_BAND_VAL(0)`。由无死区 32 位全精度累加器凭借极高的直流积分增益，平滑、自适应地克服电机静态摩擦（实测定点静差达 0.0303°，已小于 4000 CPR 编码器单脉冲 0.09° 分辨率，实质达硬件极限）。早前记录的“250”实际为起摆核的死点启动冲击电压（3.0V），并非平衡运行期的死区补偿。

### D8 🔴 增量编码器 Z 相单圈清零破坏多圈软限位，且清零未同步复位差分前值

- **症状**：在具有多圈旋转特性的倒立摆系统中，即使转臂连续单向飞转绞线，±2 圈（±8000 脉冲）的防绞线软限位保护也绝不触发；此外按 KEY2 标定转臂位置时，电机会莫名剧烈狂抖震颤。
- **根因**：
  1. 顶层例化误开 `USE_Z_INDEX = 1`。Z 相每转 1 圈（4000 脉冲）即强行复位计数器，`pulse_count` 绝对值永远无法达到 8000，导致软限位判定逻辑形同虚设；
  2. `encoder_quad_reader.v` 在执行清零条件时，只清零了当前脉冲计数 `pulse_count <= 0`，却**遗漏了 `pulse_count_prev`**。在随后的 1ms 测速拍中，`delta_pulse = 0 - pulse_count_prev` 产生数千脉冲的负向虚拟阶跃，测出几千 rad/s 的假速度冲击，直接打满 PWM 输出。
- **正确做法**：
  1. 顶层显式设置 `.USE_Z_INDEX(0)`，安全屏蔽悬空或单圈脉冲的 Z 相，确保多圈软限位有效；
  2. 凡清零 `pulse_count`，必须同步复位 `pulse_count_prev`、`delta_pulse`、`raw_dalpha_q16`、`dalpha_rad_s_q16`。

### D9 正弦模式切换未回零平滑造成命令阶跃冲击

- **症状**：在定点偏角位置（如 +45° 或 -45°）按键切换至 mode 3（0.2Hz 正弦连续跟踪）时，摆杆猛烈后仰甩荡甚至跌落。
- **根因**：切入 mode 3 瞬间，`time_cnt_5s` 直接置 0，正弦查找表从初相 0°（`sin=0`）开始输出，导致目标位置 `alpha_ref_q16` 在 1 个时钟周期内从 45° 阶跃为 0°，注入了 45° 的位置阶跃冲击。
- **正确做法**：`traj_gen.v` 增加平滑状态机。切入 mode 3 时，若当前设定值不在 0°，保持正弦初相并复用斜坡发生器先平滑回到 0°；到达 0° 瞬间再无缝激活正弦轨迹跟踪。

### D10 🔴 官方 FAQ 90g 摆杆/转臂大动量接入与位置/阻尼解耦四阶平滑软启动

- **症状**：将动力学参数对齐官方 FAQ 最新规格（摆杆长 15cm/重 90g，转臂长 15.2cm/重 90g）后，起摆能够在 3.8s 成功泵入能量达到倒立顶峰并触发进入 BALANCE 态，但切入自平衡瞬间摆杆发生剧烈反甩，|$\theta$| 迅速冲过 22° 门限导致跌落。
- **根因**：
  1. **转臂大动量冲击**：摆杆与转臂质量翻倍至 90g 后，系统转动惯量显著增大。在起摆到达顶点的瞬间，转臂角速度往往处于较高的残余状态（实测达 $+4.9\text{ rad/s}$），具有极大的动量；
  2. **力矩轨竞争与饱和**：切入自平衡瞬间，若立即全额施加转臂位置刚度反馈（$K_3 \cdot \alpha_{err}$），由于此时转臂存在几十度的偏角，该项计算出的电压需求极其巨大，直接将控制输出推向 $\pm 12\text{ V}$ 饱和轨。这导致维持摆杆垂直的反馈力矩（$K_1 \theta + K_2 \dot\theta$）被完全削顶剥夺，引发摆杆甩荡失控；
  3. **若简单软化角速度阻尼则导致飞车**：若尝试在切入瞬间全局软化转臂回路（同时衰减 $K_3$ 和 $K_4$），转臂将失去制动力，在惯性带动下急剧加速飞车（实测转臂转速持续攀升至数十 rad/s，触发绞线保护或翻倒）。
- **正确做法**：**转臂阻尼刚性与位置偏差解耦的分阶渐进接入控制律**！
  1. **转臂阻尼（$K_4 \dot\alpha$）全程保持 100% 刚性反馈**，确保起摆捕获瞬间拥有充足的机械制动力矩，彻底扼制飞车倾向；
  2. **转臂位置偏差（$K_3 \alpha_{err}$）实施四阶分阶软接入**：在 `j280_hw_top.v` 引入 `catch_cnt` 计数器。切入 BALANCE 后的前 768 ms 内，分四阶逐渐增大位置反馈权重：
     - $0 \sim 255\text{ ms}$：接入 $25\%$（`>>> 2`）；
     - $256 \sim 511\text{ ms}$：接入 $50\%$（`>>> 1`）；
     - $512 \sim 767\text{ ms}$：接入 $75\%$（`50% + 25%`）；
     - $\ge 768\text{ ms}$：接入 $100\%$ 全额反馈。
- **实测效果**：
  - 起摆接杆瞬间的摆杆倾角峰值被精确压制在 **21.861° < 22.0°**（TEST B 零跌落通过）；
  - 768 ms 后全刚度接管，彻底消除积分死区与位置稳态残差，实测定点伺服稳态静差达到惊人的 **0.0303° < 0.20°**（TEST D 闭环达成）；正弦动态跟踪 RMS 误差达到 **3.8563° < 10.0°**（TEST E 闭环达成）。

### D11 🔴 官方 FAQ 明确的 WDD35D4 345° 盲区与差分测速虚假尖峰防御

- **症状**：实物起摆过程中，摆杆从下垂点连续旋转多圈。电位器滑片滑过 345° 后的 15° 绝缘间隙盲区时，输出引脚可能悬空或电平突变。
- **危害**：差分测速一拍内测出巨幅 $\Delta \theta$，经过 $\times 1000$ 差分测速计算出高达 **90+ rad/s 的虚假速度尖峰**，污染 IIR 滤波并使动能 $E_{kin} \propto \dot\theta^2$ 瞬间暴增，引发能量泵控制器误判“能量已过饱和”而立即停止泵能，起摆中途夭折。
- **应对准则**：
  1. **机械安装规程**：万用表量测电位器引脚阻值，确认 15° 盲区所在机械方位，必须将其安装在摆杆**正下方自然下垂点（180°）**，确保倒立平衡区（±45°）处于高线性无缝区域；
  2. **RTL 防御性限幅**：在 [`angle_sensor_reader.v`](../../furuta_lqr_ctrl/src/angle_sensor_reader.v) 的流水拍 2 中引入 `DTHETA_PHYS_LIMIT_Q16 = 32'sd2293760`（±35 rad/s 安全门限）。摆杆物理极限角速度约 20~25 rad/s，该门限既对正常起摆/平衡完全透明，又将盲区突变毛刺完全钳位，保障动能计算与 IIR 滤波免受冲击。

### D12 🔴 LQR 增益实机调优与 Testbench 容差带排斥陷阱

- **现象**：RTL 中实机调优增益 $K_1 = -87.1845, K_2 = -9.6412$ 与 Python CARE 理论解（-98.1984, -10.5681）存在约 10% 的降增益调优差异（旨在抑制 90g 接杆大动量电压饱和）。
- **陷阱**：`furuta_lqr_ctrl_tb.v` 的 Case 2 原容差门限被硬编码为 `[120, 160]`。当前 RTL 增益理论输出为 145（通过）；若后续开发者按理论连续解将增益改回 -98.2，算出的 PWM 跃升至 163，将超出 160 导致单测意外报红！
- **正确做法**：
  1. 绝不可单边盲目改动 RTL 增益或随意收紧/放宽 TB 容差；
  2. TB 容差门限拓宽为 `[120, 175]`，居中兼容实测调优值（145）与理论解（163），并在注释中显式记录双重基准。

## E · 时序与资源

### E1 🔴 DSP 100% 满载，零余量

- **症状**：DSP 20/20，任何新增乘法需求都无法实现。
- **根因**：LQI 核用 Q16 × Q16 直接相乘，综合器推断出 **MULT36X36**，每个吃 2 个 DSP。
- **正确做法**：**降位宽到 Q10**，使乘法落入 **MULT18X18**（每个 1 DSP）。降位宽后与 Python CARE 解的增益误差 **<0.01%**，完全可接受。
- **结果**：DSP 100% → **88%**（余 2.5 个），MULT36X36 清零。
- **连带注意**：降位宽会改变中间量尺度，**必须同步所有移位量**——这就是 B1 那个 65536 倍错误的来源。

### E2 🔴 时序崩溃：slack 0.001 ns（Fmax 50.001 MHz）

- **症状**：功能全对，但最小 setup slack 只剩 **0.001 ns**，裕量 **0.002%**。任何布局变动都可能直接违例。
- **定位方法**：读 `impl/pnr/*_tr_content.html` 的 `Setup_Slack_Table`，看最差路径的 **From/To Node** 与 **Logic Level**。本例 Logic Level = 18。
- **根因**：起摆核里 tanh 四段折线的**比较链**串在 64 位乘法之后。
- **正确做法**：**拆流水**。把折线计算插一级寄存器，Logic Level 18 → 8，Fmax → **57.685 MHz**（slack 2.665 ns）。
- **⚠️ 拆流水的代价**：**延迟变多了一拍**。必须同步修改所有延迟断言（见 C10）与下游时序预期。

### E3 修好一个时序问题，只是把关键路径转移了

- **现象**：起摆核拆流水后，最差路径从 `u_swing_ctrl` 变成了 `u_swing_ctrl` 的 **cos 查表**链。
- **教训**：**每次改完都要重跑 PnR 并重新读最差路径**，不要假设「上次不是它就永远不是它」。
- **本例结局**：后续修改（索引改为乘法+移位）自然解除了该瓶颈，未额外拆流水。

### E4 解卷绕逻辑直接把 Fmax 打到 50.194 MHz

- **症状**：加了 B6 的最短角位移解卷绕后，Fmax 从 57.685 **崩到 50.194 MHz**（裕量 0.39%）。
- **根因**：比较 mux（±205887/205888 阈值）与 `×1000` **串在 64 位乘法之后**，全在同一条组合路径上。
- **正确做法**：拆成 **3 拍流水**（`filter_step` 从 1 位扩到 2 位，新增 `diff_raw_r` 寄存器）。
- **结果**：Fmax 恢复到 **63.357 MHz**，slack **4.217 ns**，DSP 88% 不变。

### E5 资源/时序数字要建基线表，逐轮比对

- **做法**：每轮把 `Fmax / Slack / 裕量 / Logic Level / DSP / Latch / 引脚` 记成一行，形成多轮对比表（见 [`选题一_RTL代码合规性检查报告.md`](选题一_RTL代码合规性检查报告.md) §3.1）。
- **价值**：三轮那次 slack **0.001 ns** 就是因为有二轮的 2.240 ns 作对比才一眼看出退化。**单轮数字看不出趋势。**

## F · 三条元教训

42 个具体的坑，归纳到最后只有三句话。

### F1 先校准尺子，再修东西

> 本项目最大的转折不是修好了起摆，而是**先发现测量平台自己丢了 1.42° 的数据**。

在 C4/C5 修复之前，我们拿着一个有 1.42° 系统偏置、结果不可复现的平台去评判控制器，得出过「控制器收敛慢」的错误结论。修好尺子之后，同一个控制器的误差从 10.155° → 1.1017° → 0.2302°，**而 RTL 一行没改**（前两步）。

**行动准则**：当测量结果与预期不符时，先问「尺子准吗」，再问「被测对象对吗」。具体手段：
- 给测量平台自己加断言（本项目：plant↔DUT 传感器一致性硬断言）
- 确认仿真可复现（消除调度竞态）
- 确认测量窗口对准了想测的区间（锚定实测事件，不用固定偏移）

### F2 绿灯的意义取决于断言的强度

> 「测试全绿」本身**不携带任何信息**。信息在「如果功能坏了，哪条断言会变红」。

五次假绿（C1）没有一次是「断言写错了」，全部是「断言根本没覆盖到」。具体三种形式：
- **断言太弱**：只比 1 bit（C2），或只要求「不为零」（C9）
- **断言未接线**：计数器只打印不入判决（C1-5），或 PASS 文本背书了未执行的检查（C6）
- **断言未执行**：TB 压根没跑（C1-2/3/4）

**行动准则**：每写一个断言就问「删掉对应功能，它会红吗」。每看到一条 PASS 就问「这句话我真的检查了吗」。每个「0 次异常」都要同时报告覆盖次数（C7）。

### F3 定下一个常数前，先算它的物理量级

> B1（65536 倍）、B2（索引步进不匹配）、B4（钳位 8 rad/s 导致 runaway）、B8（前馈差 10 倍）、D7（死区 75 应为 250）—— **五个灾难级缺陷全部源于「常数没回到物理量去算」**。

具体做法：
- 写下常数的**物理含义**与**推导式**，而不是只写数值（例：钳位阈值 ≥ `sqrt(4·m2·g·l2/Jp)` = 17.151 rad/s，取 32 rad/s）
- 成对常数写成**显式不变式**（例：`RAMP_VEL == RAMP_STEP × 1000`）
- 改 Q 格式时重算整条链路的移位量（B1）
- 查表时核对**索引步进 == 表步进**（B2）
- 用 Python 逐位复现定点路径，**对中间量而不只对最终输出**做比对
